# Terrain Alignment Investigation — 2026-04-01

## Status: FIX APPLIED — Needs rebake + visual verification (2026-04-03)

**Symptom:** After building Terrain3D from source (v1.1.0-dev custom build), terrain appeared misaligned with objects. Houses in Seyda Neen float above terrain.

**Root causes found and fixed:**
1. Terrain3D DLL `set_vertex_spacing()` segfault — fixed in source, DLL rebuilt 2026-04-02
2. `set_vertex_spacing()` crashes both pre-tree AND post-tree — **scale workaround** used instead (`terrain.scale = Vector3(1.828, 1, 1.828)` with vertex_spacing=1.0)
3. Terrain3D C++ `ENTER_TREE` re-enables physics processing after GDScript disables it — fixed by re-disabling AFTER `add_child()`
4. Prebaking scene had no Camera3D — Terrain3D v1.1+ crashes in `_grab_camera()` without one
5. `import_images()` position is image CORNER, not center — old center offset placed heightmap data at pixel 128 within each region. Fixed to corner + 0.5
6. Incremental `save_directory()` every 10 regions prevents DLL crash at ~50 sequential imports
7. Height queries now use `world_to_terrain_internal()` (affine_inverse) to convert world→internal coords for scale workaround
8. **import_images() Z position was SW corner, not NW corner** (FIXED 2026-04-03) — `import_images()` places pixel (0,0) at the NORTHWEST corner (min Z = most north). The formula used `-region_coord.y * size + 0.5` which is the SW corner Z. Fixed to `-(region_coord.y + 1) * size + 0.5`. This shifted ALL terrain 468m south. Fixed in terrain_manager.gd, world_data_provider.gd, generic_terrain_streamer.gd.
9. **GenericTerrainStreamer called `set_vertex_spacing()`** which crashes DLL (FIXED 2026-04-03) — removed direct call, now uses `CS.configure_terrain3d()` with scale workaround.

**Action required:** Re-bake terrain with `prebaking_manager.gd` and run `test_terrain_alignment.gd` to verify.

## Root Cause Hypotheses (Ordered by Likelihood)

### Hypothesis 1: Pre-baked Terrain Data Mismatch
**Most likely.** The terrain cache (`SettingsManager.get_terrain_path()`) contains `.res` files generated by `import_images()`. If the new DLL changed how `import_images()` or `load_directory()` internally handles coordinates, cached data from the old DLL would be misinterpreted.

**How to test:**
1. Delete the terrain cache directory
2. Regenerate terrain from scratch using the prebaking tool
3. If terrain aligns properly → old cache was stale

### Hypothesis 2: `change_region_size(256)` Behavior Changed
`coordinate_system.gd:349` calls `change_region_size(TERRAIN_REGION_SIZE)`. The new build's ocean/clipmap features may have changed the default region size or how `change_region_size()` works internally.

**How to test:**
1. After `configure_terrain3d()`, log `terrain_3d.get_region_size()` — confirm it returns 256
2. If it returns something else (e.g., 1024), region positions would be wrong

### Hypothesis 3: `import_images()` Coordinate Origin Shifted
Ocean/clipmap features in Terrain3D 1.1.0-dev may have changed the internal coordinate origin (corner vs center, axis flip, etc.).

**How to test:**
1. Create a minimal test: import one region at known position
2. Read back with `get_region_location()` and `get_height()` at known world positions
3. Compare actual vs expected positions

### Hypothesis 4: `world_to_terrain_internal()` Workaround Interference
`CoordinateSystem.world_to_terrain_internal()` uses `terrain.global_transform.affine_inverse()` to convert world coords to internal coords (accounting for the scale workaround). If the new DLL changed how the transform interacts with region placement, positions would drift.

## Architecture: Translation Layer

### Current Design (Good)
`coordinate_system.gd` is the single source of truth — contains all MW↔Godot conversion functions. This IS the "Morrowind translation layer."

### Principle for Generalist Framework
All Morrowind-specific constants (`UNITS_PER_METER`, `CELL_SIZE_MW`, axis swap) must ONLY live in `coordinate_system.gd`. No other file should contain raw MW conversion numbers. After conversion, everything works in standard Godot meters.

### OpenMW Reference
OpenMW does NOT convert to meters — it works entirely in MW units. Their `UnitsPerMeter = 69.99125109f` is only used for sound attenuation. Our meter-based framework is original design, not derived from OpenMW.

Key OpenMW constants (`inspos/openmw/components/misc/constants.hpp`):
```cpp
constexpr float UnitsPerMeter = 69.99125109f;  // 64 units per yard
constexpr float UnitsPerFoot = 21.33333333f;
constexpr int CellSizeInUnits = 8192;
constexpr float GravityConst = 8.96f;  // m/s² — devs used yards, forgot to convert
```

## ROOT CAUSE FOUND (2026-04-02)

### The DLL forcibly resets the node transform every frame

**File:** `D:/Gamedev/Terrain3D/src/terrain_3d.cpp`, NOTIFICATION_TRANSFORM_CHANGED handler
```cpp
case NOTIFICATION_TRANSFORM_CHANGED: {
    if (get_transform() != Transform3D()) {
        set_transform(Transform3D());  // Forces identity every frame
    }
    break;
}
```

Added by commit `1d646d33` (Tom Coxon, 2024-07-03). This kills any node scale, position, or rotation set from GDScript.

### Confirmed via diagnostic tests:
- `change_region_size(256)` works correctly ✓ (Hypothesis 2 eliminated)
- Height queries at correct internal coordinates return valid data ✓
- Scale set via `.scale` property IS reset to (1,1,1) every frame — even with `process_mode = DISABLED` ✗
- Per-frame scale re-application with `process_priority` does NOT help ✗ (reset at GDExtension level)
- Prebaked data is valid — just needs correct vertex_spacing for rendering and coordinate mapping

### The fix: Patch the DLL (4 changes)

**Fix 1: `set_vertex_spacing()` segfault — uninitialized `_label_parent` pointer**

Root cause: `_label_parent` (Node3D*) is declared without initialization in `terrain_3d.h:113`.
When `set_vertex_spacing()` calls `update_region_labels()` → `_destroy_labels()`, it dereferences
the uninitialized pointer → SIGSEGV.

```cpp
// terrain_3d.h:113 — initialize pointer
Node3D *_label_parent = nullptr;

// terrain_3d.cpp:270 — guard _destroy_labels()
void Terrain3D::_destroy_labels() {
    if (!_label_parent) { return; }  // ADD THIS
    Array labels = _label_parent->get_children();
    // ... rest unchanged

// terrain_3d.cpp:599 — guard update_region_labels()
if (_label_distance > 0.f && _data && _label_parent) {  // ADD _label_parent check
```

**Fix 2: Transform reset (optional but recommended)**

```cpp
// terrain_3d.cpp:1162 — only reset position, not scale
case NOTIFICATION_TRANSFORM_CHANGED: {
    Transform3D t = get_transform();
    if (t.origin != Vector3()) {
        t.origin = Vector3();
        set_transform(t);
    }
    break;
}
```

**Fix 3: `_initialized` gate on `set_vertex_spacing()` subsystem rebuild**

```cpp
// terrain_3d.cpp:744 — prevent subsystem access before initialization
if (_initialized && _collision && _data && _instancer && _material.is_valid()) {
```

**Fix 4: Skip `_collision->build()` in `set_vertex_spacing()`**

Synchronous collision rebuild after spacing change crashes. Deferred to next `update()` or `snap()`.

### DLL still has a fundamental `set_vertex_spacing()` bug (2026-04-02)

Despite all 4 fixes, `set_vertex_spacing()` **still crashes** in this Terrain3D v1.1.0-dev build:
- **Pre-tree:** `_initialize()` during ENTER_TREE crashes when `_vertex_spacing != 1.0` (clipmap builder can't handle non-default spacing during initial setup)
- **Post-tree:** Calling `set_vertex_spacing()` after initialization leaves clipmap/mesher in a corrupted state → subsequent `import_images()` segfaults

**Resolution: Scale workaround** — leave `vertex_spacing` at default 1.0, set `terrain.scale = Vector3(1.828, 1.0, 1.828)`. Fix 2 (transform preserves scale) makes this persist.

**Height queries require coordinate conversion:**
`get_height()` operates in internal space (vertex_spacing=1.0), so world positions must go through `terrain.global_transform.affine_inverse()` first. This is handled by `CoordinateSystem.get_terrain_height()`.

### Session 4 (2026-04-03): ROOT CAUSE FOUND AND FIXED
- **Root cause: Z import position was SW corner, not NW corner.** `import_images()` places pixel (0,0) at the NORTHWEST corner (min Z = most north in Godot). Formula used `-region_coord.y * size + 0.5` which gives the SW corner. Fixed to `-(region_coord.y + 1) * size + 0.5`.
- This shifted ALL terrain data one region south (468m), causing objects to float above wrong terrain.
- The old center offset (`- size/2 = -128`) accidentally partially compensated for Z while being wrong for X. The Session 3 "fix" to corner (`+0.5`) improved X alignment (8/10) but broke Z completely.
- **Fixed in:** terrain_manager.gd, world_data_provider.gd, generic_terrain_streamer.gd (sync + async paths), import_single_cell (local + global modes)
- **Also fixed:** GenericTerrainStreamer called `set_vertex_spacing()` which crashes DLL → now uses `CS.configure_terrain3d()` with scale workaround
- **Also fixed:** GenericTerrainStreamer used world-space positions for import_images() with vertex_spacing=1.0 → now uses internal-space positions based on actual vertex_spacing
- **Test results (fresh terrain):** Heights match to 0.0000m diff across all test cells. Cached terrain shows 10-14m errors confirming stale data from old formula.
- **Action required:** Rebake terrain cache, then run `test_terrain_alignment.tscn` to verify.
